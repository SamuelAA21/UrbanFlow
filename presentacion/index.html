Proyecto final · Big Data

UrbanFlow

Análisis de movilidad urbana y predicción de demanda de transporte con Apache Spark y Machine Learning, sobre millones de viajes reales de taxi de Nueva York.

MotorSpark 3.5 · PySpark
InfraestructuraClúster en AWS
DatosNYC TLC 2025
Presentar el proyecto en una frase: usamos Spark en un clúster real de AWS para procesar millones de viajes de taxi, encontrar patrones y predecir la demanda por zona y hora.

El problema

¿Dónde y cuándo se van a necesitar taxis?

🌃¿Qué zonas se mueven más los viernes por la noche?Patrones por zona, día y hora.
🕗¿Qué horarios concentran la actividad?Picos de la semana y diferencias entre boroughs.
🔮¿Cuántos viajes habrá mañana a las 8:00 en una zona?Predicción con Machine Learning distribuido.

Las predicciones estiman viajes registrados esperados, no la demanda insatisfecha.

Paso 1–3: las tres preguntas que guían el proyecto. Útil para flotas, conductores y planeación urbana: ubicar vehículos antes de que aparezca la demanda.

¿Por qué Apache Spark?

Un solo motor distribuido para limpiar, consultar, aprender y procesar en vivo

⚡En memoriaEvita escribir a disco entre etapas, a diferencia de MapReduce.
🧩ParticionesLos datos se dividen y se procesan en paralelo en los workers.
🧠SQL · MLlib · GraphXSQL y DataFrames optimizados por Catalyst, modelos y grafos que escalan.
🌊Structured StreamingLa misma API para datos que llegan continuamente.
Conectar con la clase: el stack de Spark es Spark Core más cuatro librerías sobre el mismo motor: Spark SQL, MLlib, Structured Streaming y GraphX. UrbanFlow usa las cinco piezas (GraphX a través de GraphFrames, porque GraphX no tiene API en Python).

Arquitectura

Clúster Hadoop + Spark desplegado en AWS con un solo comando

Paso 1: 4 máquinas EC2, Hadoop (HDFS + YARN) y Spark sobre YARN. Paso 2: los datos se descargan dentro de AWS directo a HDFS, no pasan por el computador. Paso 3: al computador solo bajan resultados pequeños. Todo se crea con un script y se elimina con otro (sin costos residuales).

Grafos · GraphX

    
La ciudad como grafo: PageRank de GraphX encuentra las zonas centrales

    

      
PageRank sobre el grafo troncal (los 3 destinos principales de cada zona)

      
    
        
  • Zonas = vértices · viajes origen → destino = aristas
    • 
        
  • PageRank y Label Propagation de GraphXGraphX no tiene API en Python: GraphFrames la expone sobre DataFrames y llama a org.apache.spark.graphx.lib (verificado en el jar).
    • 
        
  • Búsqueda de patrones: (a)→(b) y (b)→(a)
    • 
        
  • Comunidades con Label Propagation
    • 
      

    

    
PageRank: una zona es central si le llegan corredores desde otras zonas centrales; es el algoritmo de Google aplicado a la red de viajes. El PageRank de GraphX no usa pesos y la red está muy conectada (el 71 % de los pares posibles de zonas tiene al menos un viaje; cada zona tiene unos 28 corredores fuertes), así que se ejecuta sobre el grafo troncal: cada zona conserva solo sus 3 destinos principales. Con todos los corredores, Label Propagation juntaba todo en una sola comunidad. Paso 3: búsqueda de patrones con la sintaxis de motifs de GraphFrames. Paso 4: Label Propagation agrupa zonas solo por cómo las conectan los viajes, sin conocer los boroughs.

  


  
  

    
Machine Learning con MLlib

    
Árboles distribuidos de MLlib para predecir viajes por zona y hora

    

      
    
        
  • Malla completa zona × horaLas horas sin viajes cuentan como 0 (la demanda baja también se aprende).
    • 
        
  • VariablesHora, día, festivo, viajes de ayer y de la semana pasada (funciones de ventana), perfil histórico de la zona.
    • 
        
  • Validación temporalSe entrena con el pasado y se evalúa con los últimos 14 días, que el modelo nunca vio.
    • 
        
  • Random Forest vs Gradient-Boosted TreesCon maxBins = 32 (por defecto) el bosque perdía contra el promedio histórico: discretizaba demasiado las variables. Con 256 lo supera.

Importancia de las variables

    

    
Evitar la fuga de información: el perfil histórico se calcula solo con datos de entrenamiento y la partición es por fecha, no aleatoria.
